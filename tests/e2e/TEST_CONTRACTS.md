# E2E Test Contracts

This file records the strict implication of each implemented E2E test.

The rule is intentionally narrow: if a test passes, only the listed implication
is proven. Scenario names, comments, and business intent do not expand the
contract unless the test asserts it directly.

## Reading This File

- **Strict implication** means what is mechanically proven by the assertions.
- **Not proven** lists nearby claims that remain untested by that spec.
- Harness tests prove provider/test infrastructure, not app business behavior.
- Synthetic signed webhook tests prove our webhook handler path, not Stripe's
  real event delivery pipeline.

## Current Coverage Limits

The implemented tests do not yet strictly prove:

- Hosted Stripe Checkout completion from the driver UI.
- Monthly subscription renewal, card update recovery, or subscription reactivation after delinquency.
- Recovery from delinquency when Stripe eventually collects payment (no implemented re-activation flow yet).
- Partial refund accounting.
- Stripe dispute or chargeback handling.
- Real Stripe CLI/Dashboard webhook delivery to the local app; current payment/refund tests use signed synthetic events with real Stripe object IDs.
- QuickBooks cleanup, voiding, or correction flows.
- Advanced Reconcile tab alignment with every Needs Review issue.
- Physical Shelly relay operation; gate tests assert app/audit side effects only.
- New-device/PIN protection for copied localStorage; the relevant test is still expected-failure.

## Updating Test Contracts

When adding or changing a spec:

1. Add a row here in the same PR.
2. Phrase the implication as "Given setup X, assertion Y proves Z."
3. Do not claim a UI/API/provider behavior unless the spec touches that exact boundary.
4. Add "Not proven" for the nearest tempting overclaim.
5. If a test is expected-failure, label it as a future desired contract, not current protection.
